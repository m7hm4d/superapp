# الخطة الموحدة — منصة التوصيل المحلي (طيار المخابز)

## Context / السياق

بناء منصة توصيل محلية لحي واحد في العراق تبدأ بالمخابز: تطبيق عميل وتطبيق بائع وتطبيق سائق (هواتف فقط) ولوحة إدارة ويب، بدفع عند الاستلام فقط. المجلد `/Users/m7hm4d/Desktop/superapp` يحتوي فقط ملف مواصفات المنتج الذي كتبه المستخدم:
[local-delivery-mvp-screen-map-ar.md](local-delivery-mvp-screen-map-ar.md)

**هذه الخطة = دمج خطتين**: ملف المستخدم هو مرجع المنتج والشاشات وآلات الحالة (الأقسام 3–14 منه)، وهذه الوثيقة تضيف فوقه البنية التقنية والقرارات المحسومة في المحادثة. عند أي تعارض بين الملف والقرارات أدناه، القرارات أدناه هي الأحدث والملزمة.

## القرارات المحسومة (تعديلات على ملف المواصفات)

1. **المصادقة**: هاتف + كلمة مرور الآن (بلا SMS). شاشتا G-01/G-02 تُبنيان بخطوة كلمة مرور، ويُضاف OTP لاحقاً خلف علم `auth.otp` عند التعاقد مع مزود SMS. دخول الإدارة: بريد + كلمة مرور قوية + TOTP MFA.
2. **المنصات**: التطبيقات الثلاثة هاتف فقط (iOS + Android عبر Expo). الويب للوحة الإدارة فقط. (يتجاوز البند 1 من الملف؛ نسخ الويب ممكنة لاحقاً لأن Expo يدعمها دون إعادة كتابة.)
3. **الدفعات**: كما في الملف — الخادم ينشئ دفعة من 1–3 طلبات `READY` من المخبز نفسه، قبول ذري للدفعة كاملة، دفعة نشطة واحدة لكل سائق. (يلغي نموذج "السائق يختار حتى 4 طلبات" من الخطة التقنية السابقة.)
4. **التحقق**: PIN فقط في الطيار (استلام الدفعة، تسليم كل طلب، التسوية) — QR مؤجل.
5. **العمولة**: قيد `platform_commission` موجود في الدفتر من اليوم الأول بقيمة 0 في الطيار.
6. **حالة EXPIRED**: ليست حالة — انتهاء مهلة قبول المخبز = إلغاء تلقائي بسبب "انتهاء المهلة" (متوافق مع الملف).
7. **اللغة**: بنية i18n من اليوم الأول (قاموس مكتوب الأنواع ar/en)، العربية كاملة في الطيار والإنجليزية تعبئة تدريجية P1.

## Stack المؤكد

- TypeScript كامل: 3 تطبيقات Expo (dev build — لا Expo Go) + لوحة Next.js + باكند NestJS.
- PostgreSQL + PostGIS، **Drizzle ORM** (دعم `geography(Point,4326)` عبر `customType`؛ Prisma يجعلها `Unsupported`).
- Socket.io للإشعارات الحية + Expo Push لحدثين فقط (طلب جديد للمخبز، دفعة معروضة للسائق) — مع polling احتياطي كما في الملف §10.
- خرائط MapLibre: ‏`@maplibre/maplibre-react-native` في التطبيقات، ‏`@vis.gl/react-maplibre` في لوحة الإدارة (خريطة A-03 الحية) مع `setRTLTextPlugin`. البلاطات: OpenFreeMap (`tiles.openfreemap.org/styles/liberty`) — مجاني بلا مفتاح، مركزي في `tiles.ts`.
- ملاحة السائق: فتح تطبيق خرائط خارجي (الملف §6) — لا ملاحة داخلية.
- العملة: `bigint` IQD بلا كسور، عرض `Intl.NumberFormat('ar-IQ-u-nu-latn')` ← «12,500 د.ع». خط IBM Plex Sans Arabic. RTL: خصائص منطقية فقط + `DirectionalIcon`.

## المبادئ المعمارية الأربعة (مطلب المستخدم)

1. **جاهزية التوسع**: جدول `cities` (يغطي "الحي" في الطيار: مركز + نصف قطر خدمة + أجرة توصيل) و`city_id` على الجداول التشغيلية وفهارس مركبة تبدأ به؛ `tenant_id` على `cities` فقط مع مستأجر افتراضي — التوسع لاحقاً بلا إعادة تصميم.
2. **Socket ليس مصدر الحقيقة**: الحالة في PostgreSQL عبر REST حصراً؛ كل زر فعل REST بـ idempotency key؛ الـ socket تلميح فوري يكتب في كاش TanStack Query؛ عند reconnect إعادة جلب كاملة؛ دعم `expectedVersion` (تفاؤلي) على انتقالات البائع كما في الملف §8.
3. **Feature Flags**: جدول `feature_flags` + ‏`GET /config` مخبأ + بث `config.updated`. الأعلام الأولية: `category.bakery` ✅، `category.vegetables/market/construction` ❌، `auth.otp` ❌، `customer.live_tracking` ❌، `batch.max_size` = 3.
4. **Observability**: ‏nestjs-pino بـ JSON + redaction، ‏`x-request-id` عبر AsyncLocalStorage (يظهر في شاشات أخطاء التطبيقات)، `admin_audit_log` لكل فعل إداري (الملف يشترط سبباً لكل إجراء قسري)، Sentry اختياري بالبيئة، `GET /health` عبر terminus، ونقطة تمديد OTel لاحقاً.

## نموذج البيانات (Drizzle — `apps/api/src/db/schema/`)

- `tenants`, `cities` (center، أنصاف الأقطار، `delivery_fee_iqd`، ساعات الخدمة)
- `users` (phone فريد E.164 عبر `normalizeIraqiPhone()` الموحدة، argon2id، role، status) + `refresh_tokens` (rotation + family_id لكشف السرقة) + `admin_credentials` (بريد + TOTP secret)
- `customer_addresses` (دبوس + نقطة دالة + هاتف — نظام العنونة الفعلي)
- `vendor_profiles` (`city_id`، category، `location geography` + GIST، `is_open`، ساعات، مدة تحضير افتراضية، `approval_status`) و`driver_profiles` (`city_id`، مركبة، `is_available`، `last_location`، `approval_status`)
- `products` (name_ar/en، سعر، قسم، توفر، ترتيب — snapshot يؤخذ في الطلب)
- **آلة 1 — الطلب**: `orders` (`city_id`، كود قصير، status: ‏`PENDING_BAKERY → PREPARING → READY → IN_DELIVERY → DELIVERED | CANCELLED`، مبالغ منسوخة، `delivery_location`، `delivery_pin` (4 أرقام يراها العميل)، `prep_minutes`، `version` للتفاؤلية، طوابع زمنية) + `order_items` (snapshots) + `order_events` (تدقيق كل انتقال: actor، from، to، سبب)
- **آلة 2 — الدفعة**: `batches` (`vendor_id`، `driver_id` عند القبول، status: ‏`PROPOSED → OFFERED → CLAIMED → PICKUP_CONFIRMED → ACTIVE → COMPLETED | EXPIRED | CANCELLED`، `pickup_pin` يراه المخبز، مهلة العرض) + `batch_orders` (ربط 1–3 طلبات، ترتيب التوقفات من الخادم). ‏"سائق معيّن" تُستنتج من دفعة `CLAIMED` — ليست حالة طلب.
- **آلة 3 — التسوية**: `settlements` (vendor↔driver، status: ‏`UNSETTLED → AWAITING_CONFIRMATION → SETTLED | DISPUTED`، `settlement_pin`، الطلبات المشمولة، إيصال)
- `ledger_entries` — append-only بمبالغ موقعة، **لا حذف ولا تعديل؛ التصحيح بحركة عكسية مرتبطة بالأصل** (`reversal_of_id`). الأنواع: `order_sale`، `delivery_fee`، `platform_commission` (0 في الطيار)، `cash_collected`، `settlement`، `reversal`. عند `DELIVERED` تُكتب القيود بمعاملة واحدة.
- `exceptions` (order_id/batch_id، النوع: عميل غير متاح/عنوان غير واضح/فرق نقدي…، `OPEN/RESOLVED`، المالك، القرار والسبب) — الطلب يبقى `IN_DELIVERY` حتى قرار إداري (الملف §8.1)
- `feature_flags`, `admin_audit_log`, `idempotency_keys` (مفتاح + hash الطلب + الاستجابة المخزنة — لكل كتابة من التطبيقات)

**حراس الانتقال** (الملف §8 "حراس الانتقال" يُنفَّذ حرفياً): دالة `transition()` وحيدة لكل آلة مع `SELECT ... FOR UPDATE`، والقبول الذري للدفعة `UPDATE batches SET status='CLAIMED', driver_id=$d WHERE id=$b AND status='OFFERED'` — صفر صفوف = 409. مؤقتات: انتهاء مهلة قبول المخبز ← إلغاء تلقائي؛ انتهاء عرض الدفعة ← `EXPIRED` وإعادة اقتراح.

**محرك الدفعات (جديد — أهم عمل باكند بعد آلات الحالة)**: عند تحول طلب إلى `READY`، مهمة تجميع تبحث عن طلبات `READY` أخرى للمخبز نفسه خلال نافذة قصيرة (60–90 ثانية قابلة للضبط) وتنشئ دفعة 1–3 طلبات بترتيب توقفات بسيط (الأقرب فالأقرب من المخبز)، ثم تعرضها (`OFFERED`) للسائقين المتصلين المتاحين في المدينة عبر `drivers:{city}` مع مهلة قبول. لا إعادة تركيب بعد `CLAIMED`.

## Realtime (Socket.io ‏`/rt`)

توثيق JWT في handshake. الغرف: `user:{id}`، `vendor:{id}`، `drivers:{city}`، `admin`. الأحداث تتبع جدول الملف §10 حرفياً (كل إشعار يفتح كياناً بـ id ولا ينشئ مساراً جديداً، dedup بـ `eventId`). أحداث إضافية: `config.updated`، `batch.offered/claimed/expired`.

## الواجهات — الشاشات من ملف المواصفات

بنية المونوريبو (pnpm + Turborepo + ‏`node-linker=hoisted`):

```
apps/     api (NestJS) · customer · vendor · driver (Expo، هاتف فقط) · admin (Next.js)
packages/ shared (Zod + enums + آلات الحالة الثلاث) · api-client (fetch مكتوب + hooks + socket)
          map (native + web للأدمن) · ui (NativeWind، ~12 مكون) · i18n (ar/en + formatIQD) · config
```

الشاشات تُبنى بأكواد الملف كما هي — **P0 فقط للإطلاق (39 مساراً)، وP1 بعد استقرار الطيار**:
- **العميل**: C-01…C-08 + C-11، تصفح بلا حساب والمصادقة عند أول إتمام (G-01/G-02 بخطوة كلمة المرور)، "حالات وليست صفحات" كما في الملف §4 (نفاد منتج/تغير سعر = مراجعة إلزامية، لا تعديل صامت).
- **البائع**: M-01…M-08 مع تنبيه Overlay للطلب الجديد وصوت متكرر، والتسوية بـ PIN في M-07.
- **السائق**: D-01…D-08 + D-10، دفعة نشطة واحدة كشاشة كاملة، `بانتظار المزامنة` محلياً بعد PIN صحيح أثناء انقطاع (لا يُغلق مالياً قبل ACK الخادم).
- **الإدارة**: A-01…A-11 (‏Drawer بروابط URL ثابتة، كل إجراء قسري بسبب + audit)، A-12/A-13 في P1.
- **الحالات العامة الثمان** (الملف §11: تحميل/فارغ/خطأ/Offline/صلاحية/تعارض/نجاح/انتهاء جلسة) تُبنى كمكونات مشتركة في `packages/ui` من البداية.

البيانات: TanStack Query v5 + Zustand (سلة persist، جلسة)؛ التوكنات في `expo-secure-store`؛ كل كتابة تحمل idempotency key من `api-client` تلقائياً.

التصميم يتبع ترتيب الملف §14: wireframes نصية للعميل (C-02، C-03، C-05، C-07) تُعتمد قبل أي تصميم بصري، ومراجع Mobbin في §13 كأنماط لا كنسخ.

## مراحل البناء

- **M1 — الهيكل + نواة الباكند**: المونوريبو، `packages/shared` (آلات الحالة الثلاث + الحراس)، NestJS: ‏Drizzle + cities/tenants + auth (كلمة مرور + rotation + ApprovedGuard) + آلة الطلب + المؤقتات + flags + `GET /config` + pino/request-id/health/audit + idempotency، وseed: مدينة، 6 مخابز ببغداد بإحداثيات حقيقية، منتجات عربية، سائقان، طلبات بكل الحالات. ✅ *القبول: عبر curl، طلب يمر بكل الحالات والانتقالات غير الشرعية مرفوضة و`order_events` كامل وكل سطر log فيه request-id.*
- **M2 — محرك الدفعات + التسويات (باكند)**: التجميع 1–3 من مخبز واحد، العرض بمهلة، القبول الذري، PINات الاستلام/التسليم/التسوية، الدفتر والقيود الثلاثة + العمولة 0، الاستثناءات. ✅ *القبول: e2e — طلبان READY من مخبز واحد يتجمعان بدفعة، سائقان يتسابقان فيفوز واحد، استلام بـ PIN، تسليم أحدهما وفتح استثناء للآخر، والتسوية تصفّر العهدة؛ حركة تصحيح تنشئ قيداً عكسياً.*
- **M3 — تطبيق العميل**: C-01…C-08 + C-11، خريطة/قائمة، تصفح ضيف، سلة وإتمام COD، تتبع حي بخط زمني + PIN التسليم. ✅ *القبول: طلب حقيقي من التطبيق يظهر تتبعه حياً أثناء دفع حالاته من الـ API.*
- **M4 — تطبيق البائع**: M-01…M-08، تنبيه صوتي خلال ثانيتين، قبول بمدة تحضير، جاهز، تسليم الدفعة للسائق، السجل والتسوية بـ PIN. ✅ *القبول: الطلب يرن عند البائع، يصل READY، وبعد تسليم الدفعة تظهر المبيعات ويُسوَّى النقد بـ PIN.*
- **M5 — تطبيق السائق**: D-01…D-08 + D-10، عرض الدفعة بمهلة، الاستلام بـ PIN، مسار التوقفات بترتيب الخادم + فتح خرائط خارجية، التسليم بـ PIN مع المبلغ، `بانتظار المزامنة`، سجل COD. ✅ *القبول: السيناريو الثلاثي الكامل — دفعة من طلبين، تسليم + استثناء، وكل الدفاتر صحيحة.*
- **M6 — لوحة الإدارة**: A-01…A-11 (بريد + MFA، مركز التشغيل، الخريطة الحية، الطلبات بـ Drawer، الموافقات، الدفعات، COD والتسويات، الاستثناءات، الإعدادات/الأعلام + audit). ✅ *القبول: موافقة بائع وسائق جدد فيعملان؛ حل استثناء بقرار موثق يظهر في audit؛ تفعيل علم "خضار" يظهر فوراً في تطبيق العميل بلا نشر.*
- **M7 — التقوية والإطلاق**: تدقيق RTL، الحالات العامة الثمان في كل شاشة، reconnect + polling احتياطي، Sentry، Expo Push للحدثين، بناء EAS، نشر Docker Compose (‏API + PostGIS + Caddy + healthcheck) + لوحة الإدارة، سكربت e2e على البيئة المنشورة. ✅ *القبول: e2e يمر على الباكند المنشور وAPK يكمل طلباً حقيقياً على هاتفين.*

## التحقق النهائي

1. اختبارات e2e للباكند تُكتب مبكراً: آلات الحالة الثلاث، سباق قبول الدفعة، idempotency (إعادة إرسال نفس الكتابة لا تكرر)، القيد العكسي.
2. التشغيل محلياً: `docker compose up db` + ‏API (3000) + admin (3001) + التطبيقات الثلاثة عبر dev builds على منافذ Metro ‏8081–8083 والهواتف عبر IP الشبكة.
3. سيناريوهات القبول لكل مرحلة أعلاه، وأهمها الثلاثي في M5.
4. فحص المبادئ: قطع الشبكة أثناء دفعة نشطة ← `بانتظار المزامنة` ثم مصالحة صحيحة؛ تبديل علم ← وصول فوري؛ كل فعل إداري في audit.

## أخطار مقدَّمة (أسبوع أول)

- `maplibre-react-native` داخل dev build على iOS وAndroid.
- Metro + pnpm hoisted في المونوريبو، وانضباط 3 منافذ Metro.
- سباق قبول الدفعة وidempotency (اختبارات تُكتب أولاً).
- نافذة تجميع الدفعات (60–90 ثانية) قد تحتاج معايرة ميدانية — قيمة config لا كود.
- `normalizeIraqiPhone()` واحدة في `shared` تُستخدم في كل مكان حتى الـ seed.
